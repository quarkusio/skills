What is Quarkus?

A Kubernetes-native Java framework built on 4 principles

Before diving into the migration tool, let me quickly set the stage on what Quarkus is. Quarkus is a Java framework built around four principles. First, Developer Joy — removing friction from the developer experience with live reload, unified configuration, and minimal boilerplate. Second, Kubernetes Native — designed from the ground up for the cloud, with fast startup, low memory footprint, and built-in container-first support. Third, Best of Breed Libraries — it integrates with the best libraries in the ecosystem: Hibernate, RESTEasy, Vert.x, MicroProfile, and many more. And fourth, Imperative and Reactive — it has a reactive core based on Vert.x, but you are never forced to write reactive code. You can use the imperative model you're used to, and the reactive engine handles the rest underneath. This is the framework we're migrating Spring Boot applications to.

So why migrate? Let me show you real numbers from the same application running on the same hardware. In JVM mode, the headline is throughput: Quarkus delivers 30,000 requests per second versus 6,500 for Spring Boot — almost 5 times more. It also starts twice as fast and uses 36% less memory. In native mode the gap widens further — 135 milliseconds to start versus almost a full second. What does this mean for cloud cost? Quarkus uses 4 times less memory, so it fits in a much smaller instance. And Spring Boot under load produces errors when memory is tight, so in practice you need two instances to match the reliability. The result: roughly 8 times cheaper per instance in the cloud. With hundreds of microservices, that adds up fast. More details on the migration path at quarkus.io/spring/migrate.

The Migration Problem

Migrations are hard · regardless of the target

It's not just about frameworks

  • Major version upgrades · Spring Boot 2 → 3, Java EE → Jakarta EE
  • Framework changes · Spring → Quarkus, Spring → Micronaut, etc.
  • JDK modernization · adopting Java 21+, new language features
  • Legacy environments · public sector & enterprise stuck on old versions

Why migrations stay blocked

  • Manual, error-prone, expensive
  • A medium app takes 2-4 weeks of developer time
  • Hard to estimate ROI → decision-makers say no
  • Teams defer indefinitely → technical debt grows
Modernizing Java applications should not be a difficult project · it should be the standard path.
The tooling needs to make it easy, predictable, and low-risk.
Before talking about our specific tool, let's zoom out. Migrations are a universal pain in the Java world — and it's not just about switching frameworks. Even upgrading from Spring Boot 2 to 3 is a major effort. Moving from Java EE to Jakarta EE. Adopting a newer JDK. Many enterprises, especially in the public sector, are stuck on old versions because updating is already a project in itself. The pattern is always the same: it's manual, it's error-prone, it's expensive, and it's hard to estimate the cost upfront — so decision-makers defer it, and technical debt keeps growing. Our belief is that modernizing Java applications should not be seen as a difficult project, but as the standard path for the industry. And the way to get there is tooling that makes migrations easy, predictable, and low-risk. That's what we're building — and while our first focus is Spring Boot to Quarkus, the approach applies more broadly.

What We Built

We evaluated different tools and approaches · AI changed everything

1. Started with deterministic tooling · OpenRewrite, mtool 2. Evaluated multiple solutions: AI-based and non-AI 3. AI dramatically changed how we develop · we embraced the shift 4. Created a SKILL · the best of both worlds
So how did we get here? We started by building deterministic tooling — mtool, OpenRewrite recipes — the traditional approach to migrations. We evaluated different tools and solutions, both AI-based and not. But then the AI shift happened. AI coding agents became dramatically better at understanding and transforming code. We realized that instead of writing thousands of transformation rules, we could encode our migration expertise into a skill — a set of structured instructions that teaches an AI agent exactly how to perform the migration. So we embraced that change and created the migration skill. It's open source, at quarkusio/quarkus-skills, and it works with Claude Code, opencode, pi, and other AI agents. The key insight is that it's not a one-shot prompt — it's a modular, gate-driven process that combines our deep knowledge of both Spring and Quarkus with the flexibility of AI.

Two Strategies

Spring Compatibility mode (low risk) or Full Quarkus mode (full performance). The customer chooses based on their risk appetite.

Let me give you a closer look at what the skill actually is. It's a set of structured instructions — think of it as encoding the expertise of a Quarkus migration consultant into a reusable tool. It tells the AI agent step by step how to analyze the Spring Boot project, which modules to migrate, what to check after each step. It's open source at quarkusio/quarkus-skills, and it works with multiple AI agents — including IBM's own Bob, which is important because it means we can offer this as a fully IBM-supported solution. It also supports two migration strategies — Spring Compatibility for low-risk migrations, and Full Quarkus for teams that want the full performance benefits.

Two Migration Paths

Customers choose based on their risk appetite and timeline

Spring Compatibility

Recommended for most enterprise migrations

  • Uses quarkus-spring-web, quarkus-spring-di, quarkus-spring-data-jpa
  • Keeps Spring annotations and Spring code
  • Minimal code changes, lower risk
  • Incremental path to full Quarkus later

Full Quarkus

For teams ready to go all-in

  • Replaces all Spring with JAX-RS, CDI, Panache
  • Native Quarkus APIs throughout
  • Best performance and smallest footprint
  • More changes, but cleaner result
This is important for customer conversations. We offer two paths. Spring Compatibility mode uses Quarkus's own Spring compatibility extensions — the app keeps its Spring annotations but runs on Quarkus. Minimal code changes, lower risk. Full Quarkus mode replaces everything with native Quarkus APIs — JAX-RS, CDI, Panache. More work, but you get the full Quarkus experience and best performance. Most enterprise customers will start with compatibility mode and migrate to full Quarkus incrementally.

How It Works

Modular, gate-driven · compiles after every module

JDK Check → Build → Code → Frontend → Testing → Cleanup

Automatic Gate System

  • Each module has a gate condition evaluated automatically
  • No Frontend? Frontend step skipped
  • Compile check after every module

Reference Files

  • dependency-map.md · starters → Quarkus
  • annotation-map.md · Spring → CDI/JAX-RS
  • config-map.md · properties mapping

Git workflow: branch per run · main stays intact

The skill doesn't just throw everything at the AI and hope for the best. It's modular — there are six modules: JDK verification, build migration, code migration, frontend/template migration, testing, and cleanup. Each module has a gate: a condition that's evaluated automatically. If there are no Thymeleaf templates, the frontend module is skipped. After each module, it compiles the project to make sure nothing is broken before moving to the next one. Reference files: dependency-map (Spring starters to Quarkus), annotation-map (Spring annotations to CDI/JAX-RS), config-map (application.properties keys).

The Vision: mtool + AI = Hybrid

Cheaper, more deterministic, more reproducible migrations

Deterministic (mtool) AI (skill) Deterministic (validators)
mtool: Analyze → mtool: Transform → AI: Migrate complex logic → Validators: Verify

mtool · what it does

  • Analyzes Spring code: deps, annotations, patterns
  • Transforms deterministically: imports, deps, annotations
  • Same input = same output, every time
  • No AI tokens, no variability

AI skill · handles the rest

  • Controller logic and rewrites
  • Template conversion (Thymeleaf → Qute)
  • Contextual decisions (strategy, edge cases)
  • Test migration and config reasoning
Goal: mtool handles the mechanical work → AI focuses on what truly needs intelligence → migrations become cheaper and more reproducible
Now let me talk about where we're heading. Pure AI migration works, as you've seen, but we want to make it cheaper and more deterministic. That's where mtool comes in. mtool is a deterministic tool that performs a deep analysis of the Spring Boot project — dependencies, annotations, patterns, code structure. The key idea is that mtool gives superpowers to our AI skill. It provides the agent with a rich, structured analysis of the codebase before the migration even starts. The AI doesn't have to guess or discover what's in the project — mtool tells it exactly what's there. With that better context upfront, the AI makes fewer mistakes and the migration becomes cheaper because the agent needs fewer tokens to reason about the code. And the analysis is reproducible — same input, same output, every time. Roadmap: mtool as pre-migration step feeding context to the AI, plus IBM Research validators as post-migration step verifying the result = a deterministic sandwich around the AI.
