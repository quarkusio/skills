The Migration Problem

  • 60%+ of enterprise Java runs on Spring Boot
  • Migration to Quarkus = manual, error-prone, expensive
  • Typical medium app: 2-4 weeks of developer time
  • Migration is the #1 friction point for Quarkus adoption

What migration involves

Read Spring code → Understand patterns → Rewrite to Quarkus → Fix build → Fix tests → Verify

...per file, per annotation, per config property. Hundreds of files in enterprise apps.

Two Migration Paths

Customers choose based on their risk appetite and timeline

Spring Compatibility

Recommended for most enterprise migrations

  • Uses quarkus-spring-web, quarkus-spring-di, quarkus-spring-data-jpa
  • Keeps Spring annotations in the code
  • Minimal code changes, lower risk
  • Runs on Quarkus with Spring API surface
  • Incremental path to full Quarkus later

Full Quarkus

For teams ready to go all-in

  • Replaces all Spring with JAX-RS, CDI, Panache
  • Native Quarkus APIs throughout
  • Best performance and smallest footprint
  • Full access to Quarkus ecosystem
  • More changes, but cleaner result
Most enterprise customers start with compatibility mode and migrate to full Quarkus incrementally

How It Works

Modular, gate-driven — compiles after every module

JDK Check → Build → Code → Frontend → Testing → Cleanup

Automatic Gate System

  • Each module has a gate condition evaluated automatically
  • No Thymeleaf templates? Frontend module skipped
  • No Spring tests? Testing module skipped
  • Compile check after every module — never moves forward broken

Reference Files

  • dependency-map.md — every Spring starter → Quarkus equivalent
  • annotation-map.md — Spring → CDI/JAX-RS annotations
  • config-map.md — application.properties key mapping

Git workflow: branch per migration run — main stays intact

The Vision: mtool + AI = Hybrid

Cheaper, more deterministic, more reproducible migrations

Deterministic (mtool)
AI (skill)
Deterministic (validators)
mtool: Analyze → mtool: Transform → AI: Migrate complex logic → Validators: Verify

mtool — what it does

  • Analyzes Spring code: dependencies, annotations, patterns
  • Transforms deterministically: imports, deps, annotations
  • Same input = same output, every time
  • No AI tokens, no variability

AI skill — handles the rest

  • Controller logic and rewrites
  • Template conversion (Thymeleaf → Qute)
  • Contextual decisions (strategy, edge cases)
  • Test migration and config reasoning

Goal: mtool handles the mechanical work → AI focuses on what truly needs intelligence → migrations become cheaper and more reproducible
